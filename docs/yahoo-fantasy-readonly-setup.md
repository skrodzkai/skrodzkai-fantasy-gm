# Yahoo Fantasy enrollment and weekly read operations

The enrollment/roster connector is fixed to NFL season 2026, league `420010`, and team `7`. All commands remain read-only. The separate operations module adds verified weekly roster, settings, transaction, and candidate reads. Its exported helpers provide GET-only transport and in-process token refresh; CLI output never contains credentials. Enrollment's network operations are:

- `POST https://api.login.yahoo.com/oauth2/get_token` for the authorization-code exchange or refresh grant.
- `GET` the signed-in user's 2026 NFL league/team membership from the Yahoo Fantasy API.
- `GET` the verified target team's roster from the Yahoo Fantasy API.

App `Zkzv5U7y` and its registered redirect `https://localhost:8765/callback` are setup inputs, not evidence that runtime access works. Installation, enrollment, and live roster verification must each have their own successful receipt.

## Security boundary

Client ID, client secret, refresh token, and the bound Yahoo identity live only as generic-password items in the user's default macOS Keychain under service `com.skrodzkai.fantasy.yahoo`. The identity is the Fantasy API user's GUID when Yahoo returns it. If Yahoo hides that GUID, the connector instead binds the exact owned-team key proven by the authenticated `users;use_login=1/.../teams` contract. The connector never accepts these values through command-line arguments, environment variables, repository files, or normal output. Access tokens remain in memory for one invocation. Yahoo may rotate a refresh token; the connector persists the replacement before making a Fantasy resource request and fails closed if that Keychain update fails.

The initial grant and every roster run read the Keychain. Initial grant and refresh-token rotation also change it. Those are credential/security operations and require the coordinator's or user's explicit approval before execution. Keychain prompts and Yahoo sign-in/consent are owner-controlled; they must not be automated around.

For token persistence, the connector sends one `add-generic-password` command to the documented `security -i` stdin interface, then closes the pipe. Values are hex-encoded for `-X` to prevent command parsing/injection, not to encrypt them. They never enter process arguments, shell history, files, or output. The process retains `-T ""` access restrictions. Inputs that exceed Apple's interactive line limit are rejected before spawning; write failures stop the operation. This avoids the trailing `-w` prompt, which reads twice from the controlling terminal rather than accepting one piped line. This mechanism does not authorize an agent to bypass a denied Keychain operation.

## Owner-approved setup

These steps are a runbook, not authorization to perform them.

1. In the existing Yahoo application, confirm—without changing it—that Fantasy Sports access is Read and the redirect is exactly `https://localhost:8765/callback`. Do not create another app or add scopes.
2. Enroll the existing client ID and client secret with hidden Keychain prompts. Because `-w` is the final option, `/usr/bin/security` prompts for each value rather than putting it in shell history or the process argument list. `-T ''` leaves access subject to macOS Keychain approval instead of silently trusting a broad executable:

   ```sh
   /usr/bin/security add-generic-password -U -a client-id -s com.skrodzkai.fantasy.yahoo -T '' -w
   /usr/bin/security add-generic-password -U -a client-secret -s com.skrodzkai.fantasy.yahoo -T '' -w
   ```

3. Run the bounded enrollment command from this repository:

   ```sh
   node analysis/yahoo-fantasy-readonly.mjs enroll
   ```

   The command prints Yahoo's authorization URL with a random state value. It deliberately does not open a browser or operate Yahoo UI. After the owner signs in and consents, Yahoo redirects to the registered HTTPS localhost URL. This connector does **not** start a TLS server and does not disable certificate validation. The browser is therefore expected to show a connection error; copy the complete URL still present in its address bar and paste it into the connector's hidden prompt. The connector requires the exact HTTPS scheme, host, port, path, and state before exchanging the short-lived code.

   Before persisting the refresh token, enrollment uses the new access token with the existing Fantasy read permission to request the single authenticated user and that user's owned teams. It requires one exact NFL 2026 game and exact owned team `7` in league `420010`. Yahoo's OAuth-only `xoauth_yahoo_guid` field is deprecated and is therefore optional; a returned token GUID may corroborate, but never replaces, the Fantasy ownership proof.

4. Run the read-only roster proof:

   ```sh
   node analysis/yahoo-fantasy-readonly.mjs roster
   ```

   Readiness requires all of the following in that natural run: token refresh succeeds; the authenticated Fantasy response matches the enrolled GUID when one was visible, or re-proves the exact enrolled owned-team binding when Yahoo hid it; that user owns exact team `7` in exact league `420010` for NFL season 2026; the roster response is for the resulting exact team key; and the roster is non-empty. The JSON result intentionally contains no identity value or token.

## Failure posture

Errors are short codes and never include Yahoo response bodies, callback URLs, authorization headers, or Keychain values. Multiple authenticated users, a changed visible GUID, missing exact owned-team proof, wrong season, wrong league/team, empty roster, token rotation that cannot be stored, redirect, or unexpected host fails closed. A missing or hidden GUID is accepted only when the authenticated-current-user owned-teams contract proves the exact target. There is no retry, alternate account, HTTP callback, TLS bypass, or fallback credential source.

## Weekly read operations

`analysis/yahoo-fantasy-operations.mjs` reuses enrolled refresh/identity binding and verifies the exact owned 2026 league/team on every command.

```sh
node analysis/yahoo-fantasy-operations.mjs snapshot
node analysis/yahoo-fantasy-operations.mjs candidates FA:0:25
node analysis/yahoo-fantasy-operations.mjs candidates W:0:25
node analysis/yahoo-fantasy-operations.mjs targets 33994,30121 5 2026-10-07T20:04:00.000Z
```

- `snapshot`: verified current week, league waiver settings and slot counts, current roster eligibility/selected positions/status, team-specific pending waivers/trades, and up to 25 recent completed league transactions.
- `candidates`: one league-specific free-agent or waiver page, with ownership. Follow `nextStart` until null to finish the selected pool; a single page is not the full waiver universe. Repeated/changed pages across a live scan must be reconciled by player key, not assumed atomic.
- `targets <IDs> <expectedWeek> <expiresAt>`: one bounded ownership observation for 1–25 unique canonical positive numeric Yahoo player IDs. Supply the expected current week (1–18) and a future UTC ISO timestamp with milliseconds, no more than five minutes ahead; the example timestamp must be replaced. Malformed inputs fail before Keychain access. The command reuses current-user membership and league settings verification, checks the expected week, then makes one exact league `players;player_keys=.../ownership` GET. It rejects missing, extra, duplicate or conflicting player/ownership identities and wrong league/season/week. `FA`, `W` and `owned` report the observed ownership, with player identity, owner team key, waiver date and reported status. It never traverses the pool or retries.
- Target output records the full read's `requestStartedAt`, `requestCompletedAt`, the ownership GET's `ownershipRequestStartedAt`/`ownershipRequestCompletedAt`, and caller-supplied `expiresAt`; completion must precede expiry. Expiry is never renewed. `transactionReady` is always false. This is a one-shot status observation, not an execution preflight: a fresh current UI check of exact identities, availability, locks, legal drop/slots and approval conditions remains required before any submission. Ownership does not establish locks, drop legality, official health clearance or a verified waiver-release clock.
- HTTP 429/503 stops the GET immediately without retry or sleeping. A valid `Retry-After` delta/date is reported only as sanitized `retry_after_seconds`/`retry_after_at` error context; missing or malformed headers add no context. This does not authorize a retry or polling loop.
- Missing collections, wrong league/team/week, invalid counts, duplicate players, taken candidates, or potentially truncated pending claims fail rather than pretending data is complete.
- Null status is unreported, not a health clearance. Roster-wide editability is not proof that an individual player's game is unlocked. `playerLocksVerified` remains false. Unknown eligibility cannot authorize a move.
- Waiver rules/days are not a verified processing clock; `verifiedReleaseTime` remains null. Verify the actual deadline/release in Yahoo before scheduling an execution event.
- No Yahoo projection replaces the existing custom weekly model. Match available-player keys/identities to that model and retain its season/week/source cutoffs.

### Offline roster delta verification

```sh
node analysis/yahoo-fantasy-operations.mjs verify-delta <before-snapshot.json> <after-snapshot.json> add:1001:BN,drop:1002,keep:1003
```

`verify-delta` compares two previously saved `snapshot` outputs without Keychain access or any network request. The change list is comma-separated, one token per player: `add:<id>:<slot>` (absent before, now in that exact slot), `drop:<id>` (rostered before, absent now), `move:<id>:<slot>` (retained, now in that different slot) and `keep:<id>` (retained in the same slot; its facts are echoed). Every unlisted player must be retained in exactly the same slot, and every named slot must be a configured roster position.

Each file must be a saved verified snapshot whose identity is consistent in its exact keys, not only its flags: the target team's key (`<game>.l.<league>.t.<team>`) and settings league key must name the fixed target league/team, every roster player key must carry that same game prefix, the week must be a positive integer shared by settings and roster, and `verifiedAt` must be a canonical ISO time not in the future. Otherwise the command fails with `yahoo_delta_snapshot_invalid`. Both files must share team and week, and the second must be strictly later. A missing or non-empty pending claim/trade collection fails.

A recent transaction is attributed to an add only when exactly one matching record falls between the two snapshot clocks (second resolution), is a successful single `freeagents` add to the target team, and drops only players named by `drop:` tokens. Such a record is `CORROBORATED` with its key and server time. Every expected drop must be attributed: while any `drop:` player is not dropped by a corroborated add, an add whose matching record dropped nobody is `UNCORROBORATED_DROP_UNATTRIBUTED` with no server time, and the unmatched IDs are listed in `unattributedDrops`. A matching record outside that window is `UNCORROBORATED_PRIOR_RECORD_ONLY` and is never reported as this change's server time. No record is `UNCORROBORATED_NOT_IN_RECENT`, because only the 25 most recent league transactions are read. A missing transaction list is `UNKNOWN_RECENT_UNAVAILABLE`. An in-window record with the wrong source, status, drop, key or multiplicity is `MISMATCH` and fails the comparison.

Output is one JSON result: `verdict` `PASS`/`FAIL`, exact `mismatches`, `afterAgeSeconds`, `emptyStarterSlots`, current facts for each listed player, per-add corroboration and `unattributedDrops`. An uncorroborated or unknown receipt is not evidence that an add failed; the exact roster comparison still controls the verdict. Exit status is `0` for PASS, `2` for a completed FAIL comparison and `1` with the diagnostic below for malformed input or invalid snapshots. Change-list validation precedes file reads and output preparation.

PASS proves only the exact saved-roster comparison (posture `SAVED_ROSTER_COMPARISON_ONLY_NOT_PREFLIGHT_OR_EXECUTION_CLEARANCE`). It is not freshness, preflight, transaction authority, approval, lock or health clearance, or proof of the browser-visible confirmation. Mutable final checks and the canonical decision record remain required.

### Offline bounded recovery gate

```sh
node analysis/yahoo-fantasy-operations.mjs recovery-gate <job-recovery-request.json> --out=<new-result.json>
```

This command reads explicitly named saved evidence and the original job's pinned canonical ledger; it makes no access, Keychain, network, browser, or canonical-ledger write. It is a mandatory two-phase procedure gate for an already adopted, exact Joe delegation. It does not authenticate the human behind a file or discover a canonical vault. The coordinator must first establish the actual direct approval and mounted canonical path independently, then retain the original job's trusted anchor. An arbitrary packet, copied ledger, `approvedBy` field, or successful offline result creates no authority. Every recovery-affecting state must be appended to that same canonical log; legacy prose/flags alone cannot qualify an attempt. Never backfill eligibility for an old terminal ID.

The request contains `phase` (`reserve` or `check`), `rootId`, original `jobId`, sole `executor`, `requestedAt` (canonical ISO), exact `action`, `anchor` (`path`, original `sha256`, byte `bytes`, exact `lastLine`), and `evidence`. Evidence descriptors contain explicit `path` and SHA-256 `sha256`. Paths must be regular files with no symlink components or secret-shaped names, at most 16 MiB each. The ledger is the canonical `operations/decision-log.md`, pinned before reservation. The CLI never chooses another path or resets an anchor.

Append machine records with `recoveryRecord(record)` from the operations module through the existing normal anchored append/readback route. This produces one JSON line inside a `yahoo-recovery-record` fenced block. Existing prose remains unchanged. Required records in the pinned prefix are:

- One `RECOVERY_DELEGATED`: `id`, `rootId`, `jobId`, `executor`, `approvedBy: "Joe"`, `status: "DELEGATED_TO_MODELS"`, exact `season`, `leagueId`, `teamId`, `week`, original `approvedAt` and `expiresAt`, positive measured `minimumCompletionAndVerificationMs`, `approvalSource: {reference, sha256}`, `policyAdoptionReference`, `policySha256`, `costMode: "FA_ONLY_ZERO_COST"`, `action`, `conditions`, and `recoveryBudget: {additional: 1, total: 2, attemptId: "<rootId>-recovery-1"}`. Record the delegation before the initial attempt; the actual user source and adopted policy bytes are pinned evidence. No future package inherits a budget.
- One `RECOVERY_INITIAL_STOP`: same `rootId`, `jobId`; `attemptId` equal to root; `attempts: 1`, `recoveryUsed: 0`, `status: "PRE_FINAL_TECHNICAL_STOP"`, `startedAt`, `factoryVersion`, original `factorySha256`, `baselineSha256`, and `traceSha256`. An executing, final-click, uncertain, true-denial, read/output-failed, ledger-failed, expired or already terminal attempt cannot be reclassified as this record.
- One `RECOVERY_CORRECTION_ADOPTED`: same `rootId`, `jobId`; `traceSha256`, exact `failedOperation`, precise `diagnosis`, `defectReference`, `fixReference`, `reviewReference`, `adoptionReference`, `adoptedAt`, installed `factoryVersion` and installed `factorySha256`. The installed bytes and version must both differ from the failed factory; only a newly adopted corrected version can qualify (for example, .3 or later after a traced .2 failure). A fresh instance alone does not qualify. This gate supports recovery only after a separately authorized, reviewed and adopted correction; it does not perform autonomous source repair or promise immediate repair inside a running job. Source/CI/review/install authority and proof remain the normal coordinator gates.

A `RECOVERY_JOB_STOP` record for the original job freezes every root, including account-wide rate limits and Stop observed on another action; a timer expiry does not clear it. All same-root records must name the original job. Duplicate delegation/counter/correction records, an existing `RECOVERY_RESERVED` or result, revoked/superseded/blocked states, and unknown same-root record types HOLD. Record every Stop, revocation, terminal result or ledger/read failure as an additional same-root record; it must not be hidden in a packet boolean. This deliberately freezes rather than inferring a repaired counter. A different root in the same job naming the same exact action also HOLDs, including an earlier reservation/result; action identity uses semantic field values rather than JSON key order. The budget is shared across all steps/options/resumes, and reserved before loading the new instance even if it fails before any click.

Supported exact action shapes are `{kind: "add_drop", addId, dropId, slot: "BN"}` and `{kind: "lineup_change", playerId, from: "BN", to, parentRootId}`. A child additionally requires exactly one canonical `RECOVERY_VERIFIED` record for `parentRootId` in the same job with `addedId` equal to `playerId` and `snapshotSha256` equal to the child's baseline. The verified parent's own gate freezes; it is never acquired again for a child failure.

### Saved output and failure diagnosis

Append `--out=/approved/capture/root/<event>/snapshot.json` to any operations command to save JSON instead of printing the full result. The caller verifies the mounted destination, applicable free-space floor and approved existing capture root, then prepares only the exact event leaf with mode `0700`. Do not recursively create missing ancestors, repair a mount, silently chmod an existing directory or choose a new destination. The generic CLI does not create directories or enforce a household-specific mount/root policy.

Argument/request validation and destination preflight precede all access work. An output path ending in `/` reports `yahoo_output_path_invalid` at `input`. The parent must exist and be a directory; the target must be absent, including dangling symlinks. A missing parent reports `yahoo_output_directory_missing`, a non-directory parent reports `yahoo_output_directory_not_directory`, and any existing target reports `yahoo_output_exists`. Reconcile an existing artifact locally rather than overwriting it or automatically choosing another name. Other filesystem errors retain only allowlisted categories.

JSON serialization precedes opening the file. The final write uses exclusive create (`wx`) and mode `0600`; this guards against another writer creating the target after preflight. Success prints the compatible receipt `{"output":"<requested path>","apiReadOnly":true}` only after the write completes. Successful requests alone do not establish a saved capture: reopen and parse the file, verify its mode, exact target/current week, freshness and required roster/pending/lock fields. A completed write does not guarantee power-loss durability. Races, disk failure and partial files remain possible; preserve them for local reconciliation rather than deleting or treating them as valid captures.

Operations CLI failures exit with status `1` and emit one JSON diagnostic on stderr. The static `stage` is `input`, `output_preflight`, `access`, `read_validation`, `output_write` or `receipt`. The `code` is an exact recognized Yahoo code, including current numeric HTTP status and validated 429/503 Retry-After context, or `yahoo_operation_failed`. `errorType`, `errorCode` and immediate `causeCode` use explicit allowlists; unknown values are `UNKNOWN`. Arbitrary messages, stacks, response bodies, URLs, exception paths and cause objects are never emitted. This diagnostic contract applies to the operations CLI; the standalone enrollment/roster CLI is unchanged.

`accessStatus` and `readStatus` each report `not_attempted`, `started` or `completed`; `resourceRequests` counts attempted Fantasy resource GETs, excluding token work. `access` aggregates existing Keychain reads, token refresh and possible normal refresh-token rotation persistence; a failure there does not establish which internal step failed. `persistence` is `not_attempted`, `incomplete` or `completed`. An `output_write` failure after serialization reports `incomplete`, which includes exclusive-create refusal or a possible partial file. A `receipt` failure after a successful save reports `completed`: inspect the existing file locally and do not perform another live read just to reproduce the receipt.

Only a structured failure at `input`/`output_preflight` with `accessStatus: "not_attempted"` and zero `resourceRequests` can prove zero access/remote work. Within the original event timing and limits, a missing approved event leaf may receive one network-free correction before the event's first live read. Existing artifacts require reconciliation; permissions, a missing mount, insufficient free space or an unknown cause remain HOLD. After any access/read activity, post-read write failure or unknown-stage failure, perform no extra live call during that check. Inspect only relevant local paths/artifacts, retain the last successful capture and unresolved stage/code/output status, and report the actual defect instead of assuming an API outage. There is no automatic retry, mount/access recovery, alternate credential route, new wakeup or service.

### Release browser functions

`analysis/yahoo-release-browser.mjs` holds the versioned release-window browser functions (`inspect`, `stage`, `submit`, `start`) for an already-approved FA-only leg in the one verified isolated tab. `releaseBrowserLoadSource({ binding, tab, league, team, expires, waitMs })` returns the exact text to paste into the persistent browser REPL; it defines functions only and makes no navigation or click. The factory body is self-contained, so the pasted text needs no hand edit. This module grants no decision, API write, direct HTTP, DOM-evaluate mutation, forced click or retry.

- Alarm rule: every visible snapshot line except ordinary `- link` lines is checked for stop signals (limit, denial, restriction, sign-in/password/verification or other owner prompt, error/unable/try again later). An `- iframe [attr="…"]` line is element metadata (Yahoo ad frames put script source in `name`). Only its trailing inline text is checked. The frame's rendered body follows as child lines and is checked like any other line. An iframe line that does not parse exactly as that metadata form is checked whole. Claim/waiver/bid text uses the same visible content.
- Exact drop row: `stage` scopes the drop button to a row containing the exact player-name link and requires exactly one matching row. Opponent text cannot select a player; zero or multiple exact rows stop before a drop click.
- Bounded wait: after each navigation or click the function waits up to `waitMs` for the one specific expected control or text, such as the exact final button or success paragraph. Every decision is then made from a fresh full snapshot. A Playwright `TimeoutError` or the exact generic-error message `Playwright selector deadline exceeded` (optionally prefixed by `Error: `) counts as a wait result; permission, denial, blocking or tool-access messages remain fatal. Any other rejection, such as a tool or permission denial, stops the call before any further click, with its message kept as `err`, and halts the instance. A timeout decides nothing by itself, the final button is never clicked by a stage, and nothing is clicked twice.
- Any alarm, tool error, structured pre-final locator/render failure or unconfirmed final action halts the instance: later `stage`/`submit`/`start` calls return `STOP_HALTED_AFTER_PRIOR_ALARM_OR_ERROR` without navigation. `inspect` stays read-only and available. Every result carries the version, ordered `trace` operation names/clocks/outcomes and structured pre-final `failure` category when applicable, `alarmCount`/`alarms`, `click`, `finalActionMayHaveOccurred`, `t0`/`t1` and wait durations. Only `SUBMITTED_SUCCESS_TEXT` (explicit Yahoo success text, no alarm) is success; every other final-click outcome is reconciled read-only.

Generate the paste text from a reviewed commit:

```sh
node --input-type=module -e 'import("./analysis/yahoo-release-browser.mjs").then(m => process.stdout.write(m.releaseBrowserLoadSource({ binding: "hpv2", tab: "releaseTab", league: "420010", team: "7", expires: "<approval expiry ISO>", waitMs: 10000 })))'
```
